# Machine-Learning-LLM-Forecasting-Turning-Raw-Order-Data-into-14-Day-Predictions-with-a-Mini-Repo

## This work resulted in an end-to-end mini system that takes raw data, produces a daily series, performs 14-day forecasting, and exports outputs as metrics, CSV, and plots. The biggest takeaway was not just combining individual experiments, but turning each step into something reproducible, debuggable, and extensible. The next step is to expand this mini repo by integrating stronger models such as Time-LLM, and to improve the system with strategies better suited for sparse demand—such as a two-stage setup.

### I split the time series into windows to feed the model. To let the model “see” the past, I used 96 days of history (seq_len), 48 days of context for the decoder (label_len), and a 14-day forecasting horizon (pred_len) as the target. In the early experiments, a major issue emerged: because the train/val/test split was done incorrectly, no windows could be generated for the validation and test sets, which broke both training and inference. To fix this, I changed the strategy: I first generated windows from the entire series, then split those windows into train/val/test in chronological order. This ensured that validation and test were not empty and made the system stable.At this point, the work stopped being “just a notebook that produces outputs when you run it” and started to look like a small project. So I organized the code into a mini repo. I placed the data loader and window dataset logic inside data_provider/custom.py. I managed the training flow with train.py, where the model is trained and checkpoints are saved. I moved prediction and evaluation into predict_custom.py, where I load the checkpoint, generate forecasts, invert the scaling, and export the results as CSV. Ensuring consistency in scaling was critical: StandardScaler was fitted only on the training portion, the mean/scale values were stored in the checkpoint, and inverse transform during prediction was guaranteed.On the modeling side, I tested two approaches: a transformer-based, Autoformer-like model and a simpler baseline model similar to DLinear. The goal was not to make a single model “perfect,” but to build an infrastructure where different model families can be run and compared within the same pipeline. During evaluation, I produced core metrics like MAE and RMSE, and also reported ratio-based metrics such as WAPE and sMAPE. However, with sparse data, an important reality showed up again: because a large portion of true values are zero, ratio-based metrics can explode and become hard to interpret. For that reason, I complemented the metrics with diagnostics like the zero ratio of true values, making the evaluation more meaningful.
